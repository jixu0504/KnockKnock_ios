## 一、发布定位与版本策略

### 1.1 版本与窗口（结论：两次，不是一次也不是三次）

| 版本 | 主题 | 内容 | 明确不含 | 墙钟（自 2026-11-26，含缓冲） | 目标窗口 | Gate |
|---|---|---|---|---|---|---|
| **v0.3.0** | 记得对 | A 批 + 备份 v2 + 迁移 25/26 | 一切新页面、画像、跨来源 | **3.4 周** | 2026-12-14 ~ 12-19 | G0 / G1 / G2 |
| **v0.4.0** | 看得见 | B 批 + T84a + C 批余量 | 画像、跨来源、端侧模型 | **+2.4 周** | 2027-01-04 ~ 01-09 | G3 |
| **v1.0.0** | 可信 | D 批（T84/T89/T92）+ M5 收尾 | — | **+1.6 周** | 2027-01-18 ~ 01-23 | G4 |

> 窗口未计元旦假（3 天约 +0.3 周）；完整体落在春节（2027-02-06）之前，无跨节风险。

### 1.2 为什么是两次：风险隔离，而不是价值堆叠

1. **v0.3.0 改的是「数据与召回」，v0.4.0 改的是「界面与权限」**：出事时定位手段不同（前者靠回放集指标 + 开关，后者靠 UI 自检 + 权限矩阵）。混在一版，无法判断是「检索错了」还是「页面展示错了」。
2. **迁移只做一次大动作**：用户从 schema 23 一步升到 27，是唯一不可逆的破坏性动作，必须独占一个可回滚窗口，不能与印象页改版同批。
3. **v0.3.0 的价值不「性感」但可验证**：它关掉审计里的三条 P0 —— 晋升可达（结构键 + 独立 Worker）、恢复后失忆、换模型后失忆 —— 再加事实冲突（T78）。「角色不再记错」是地基，印象页只是展示层，先上展示层会放大错误。

### 1.3 能力清单：哪些随下一版上线、哪些必须延后

| 能力 | 判断 | 理由（用户价值 vs 风险） |
|---|---|---|
| 已完成切片：维护接线/清理/重建/恢复/诊断（T62–T67）、词法 + 两阶段准入 + abstention（T70/T72 部分）、事实结构 v3 + 相反极性不合并（T75-lite/T76a-lite）、整合幂等/退避/预算（T77 切片） | 随 v0.3.0 | 纯修复与已落地切片，均有单测；不合规只回退旧行为，**不会**产生错误合并 |
| 事实字段独立列 + `memory_relations`（T69）、向量 BLOB（T71） | 随 v0.3.0 | 迁移必须一次做完；BLOB 把 8 KB/行降到 ~1.5 KB，是体积与 P95 的前置 |
| 关系语义与双时间（T78）、独立整合 Worker（T77 完整） | 随 v0.3.0 | 「过期事实不再当现状」是信任问题；晋升现挂在提取协程尾部（M2 handoff §3.5），长会话会饿死 |
| 印象一等实体 + 页面 + 纠错冻结（T81/T81a/T82/T83） | **延后到 v0.4.0** | 价值最高但主观质量最难保（计划书 R5）；G3 抽检 50 条需独立窗口 |
| 设置页 + 体检页（T86/T87） | **延后到 v0.4.0** | 与印象页共用「记忆」入口心智；保留期默认值变更需产品签字 |
| 隐私与跨角色矩阵（T84a） | 延后到 v0.4.0，**但 v0.3.0 先关默认值** | v0.3.0 把关系网跨角色召回默认关掉，用零代码成本换掉审计 X-02 的暴露面 |
| 跨来源印象（T84）、用户画像（T89） | 延后到 v1.0.0 | 计划书 §4.9 定义为可选包；画像默认 `shareScope='none'`，没 UI 等于没价值 |
| 端侧嵌入 PoC（T92） | 延后到 v1.0.0，除非 G1 不达标 | R1 触发条件见计划书 §10；PoC 结论本身即可发布内容 |

### 1.4 灰度与 TestFlight 节奏

| 阶段 | 通道 | 人群 | 观察期 | 放行条件 |
|---|---|---|---|---|
| P0 开发机 | 模拟器 `xcodebuild` + `:shared:iosSimulatorArm64Test` | 代理 / QA | 每批提交 | 失败数 = 8（只允许基线网络测试） |

| P4 App Store 提审 | — | — | 1–2 轮 | 隐私清单 / 文案 / 截图齐套 |

> **不按百分比灰度**：本项目无服务端配置中心，TestFlight 也不支持按比例放量。灰度靠「版本 + 开关」：`memory_v2_enabled`（已存在，默认 true）为总开关，`private_recall_relationship_memory`（已存在，默认 true）为跨角色开关。
> **降级阀门**：若 G1 软门槛未达标，v0.3.0 **只发 TestFlight 内部、不进商店**，商店首版顺延到 v0.4.0；代码路径不变，只改发布范围。

### 1.5 发布前提（任一不满足即不排期）

1. **TestFlight 需要付费账号**：计划书 §11.2 记「已有（¥688/年）」，但 `docs/实机签名续签指南.md` 仍按 Personal Team（`7PPJKDAPJZ`）7 天自签写 —— 两处口径不一致，发布前确认。免费签名会在 7 天长跑中途过期（表现「无法验证 App」）；续签只能覆盖安装（同 bundle id 不丢沙盒数据）。
2. **仓库内未发现 `PrivacyInfo.xcprivacy`**（`find ios -name` 无结果）。记忆抽取会把窗口原文发给用户配置的模型路由，提审前需补隐私清单与政策文案。
3. **跨角色泄露面先在 v0.3.0 关掉**：`private_recall_relationship_memory` 默认 true（`SettingsRepository.kt:463`），关系网通道可把 A 角色私聊记忆注入 B（审计 X-02）。T84a 未做前建议默认改 false，并在体检页注明「关系回忆下一版开放」。
4. **58 路径未提交、无 tag**：发版前按主题分提交并打 `v0.3.0-rc1`，保证「构建产物 = 源码」。

### 3.2 迁移顺序与执行形态（关键区分：**迁移原子，重建可续跑**）

| 迁移 | 内容 | 形态 | 可中断 | 回滚 | 版本 |
|---|---|---|---|---|---|
| `24.sqm` | 词法四表 + 语料统计 | 纯 DDL，事务内 | 杀进程 = 整笔回滚重跑 | 事务回滚，无损 | v0.3.0（已实现） |
| `25.sqm` | 事实列（`subject/predicate/object/polarity/qualifiers/fact_key/valid_from/valid_to/recorded_at/time_source/conflict_status/salience`，全带默认值）+ `memory_relations` + 实体三表 | 纯 DDL | 同上 | 同上 | v0.3.0 |
| `26.sqm` | `vector_memories_v2`（BLOB + 维度/格式/签名）+ `memory_vector_migration_state` | DDL 在事务内；**数据搬迁在后台**，状态机 `pending→copying→validating→switched→cleanup_old` | **搬迁可中断**（cursor + 每批提交） | `phase` 退回 `pending`，旧表保留 ≥1 个版本周期 | v0.3.0 |
| `27.sqm` | 印象四表（impressions / evidence / suppressions / history） | 纯 DDL | 是 | 空表，零损失 | v0.4.0 |
| `28.sqm` / `29.sqm` | `memory_recall_log`（默认关闭）/ 画像两表 | 纯 DDL | 是 | 空表或可 `DROP` | v0.4.0 / v1.0.0 |

**三条硬规则**：① 迁移里只允许 DDL 与 `ADD COLUMN ... DEFAULT`，禁止在迁移事务里解码 JSON、跑嵌入、写倒排 —— 历史数据补全一律走 T64 重建任务（分批 200、可取消、有进度）。② 旧数据不伪造时间（§9.2）：`valid_from/valid_to = NULL`、`time_source='unknown'`、`recorded_at = 原 createdAt`、`fact_key` 用占位指纹 + `fact_kind='freeform'`、无证据不写 `source_message_ids`。③ 已发布的迁移文件只增不改。

### 3.3 首启「23 → 27」的一次性风险与做法

v0.2.0 用户升到 v0.3.0 时，**一次冷启动连跑 4 个迁移**（24/25/26 DDL + 26 搬迁入队），是整个发布里最危险的 30 秒。

| 措施 | 做法 |
|---|---|
| 迁移前自动备份 | DB open 前把 `rhodes.db` 复制到 `Application Support/backups/pre-migration-<schema>.db`，保留 1 个版本；失败时提示「可回退到本机备份」 |
| 迁移后置标记 | 置 `memoryIndexRebuildPending`（沿用 T65 机制），由 T64 分批重建兜底，**首启不做嵌入** |
| 首启不阻塞 UI | 迁移只做 DDL；界面先可用，体检面板显示「索引整理中（已处理 n/N）」 |
| 超时降级 | 单次重建限批 100×3（与 `A7Glue.repairIndexIfNeeded` 现实现一致）；超时落 checkpoint，下次活跃继续 |
| 故障注入验收 | T88a 必测：任一批次杀进程、切换前后 ID 无丢失（计划书 §7 T88a） |

### 3.4 旧备份恢复与回滚预案

| 场景 | 要求 / 动作 | 数据影响 |
|---|---|---|
| v0.2.0 备份（v1 格式）导入 v0.3.0 | 必须成功：新表为空、旧字段原样 | T88 未做 = **v0.3.0 硬前置**（否则「升级后能备份，恢复却丢新表」） |
| v0.3.0 备份往返 3 次 | 数据一致；恢复后置重建标记、不强制 `archived`（T65 已修） | 无损 |

### 4.3 时机表 + BGTask 边界

| 时机 | 动作 |

### 6.1 G0–G4 在本版本的可完成性
