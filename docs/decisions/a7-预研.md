# A7 自动化互动预研：拆分（保留 2 项）vs 整体移植

- 预研人：a7-presearch（T7）。基线：RhodesLink @ ios-port（tag v1.14.27-android-baseline，3642d2c），全程只读静态分析（read/grep），未构建、未改动仓库。
- 依据：计划书 v1.1 补充裁决 3（A7）。保留「动态定时回复 MomentReplyWorker」+「记忆维护 ContextMaintenanceWorker」；默认不移植每日动态 / 主动私聊 / 免打扰时段 / 手动回复定时器；若拆分所需改动 ≥ 完整移植的 80%，则整体移植。
- **结论（建议）**：**拆分移植，不触发整体移植**。拆分工作量估算 5.0–7.5 代理日，整体移植 11.5–17.0 代理日，比值约 **43%–65%**，显著低于 80% 触发线。关键原因见 §5：拆分必须的「调度栈」是薄层且与 A1 群聊自动互动共享；两项保留功能的提示词/记忆管线本就属于动态广场与记忆子系统的前台路径（随主功能移植）；4 项弃项的主体是领域逻辑（日计划器 / 主动生成），不是调度栈。

### 发现 1：Android 已有「前台补算」原语，iOS 语义是平移而非发明
- MomentReply 双通道：WorkManager 与进程内协程同时 arm（`MainViewModel.kt:2847-2859`），进程存活时由协程执行、被杀后由 WorkManager 恢复——说明该功能语义是「尽快 + 拟人延迟」，不依赖准点。
- 每日计划「补建」：`DailyContentScheduler.ensureTodayPlanSuspending` 同时被周期 worker、每次投递 worker 和 MainViewModel init（`:706`）调用，幂等（`daily_content_planned_$cycle` 标记 `:61/:129`）；计划器自带「迟建铺开」恢复逻辑（`:229-241`）——Android 端同样不假设 WorkManager 准点。
- 启动重挂三件套集中在 `MainViewModel.kt:620-639` 一个 init 块内（手动回复 / 动态回复 / 记忆维护），iOS 侧即「app 启动时重挂」清单。

### 发现 2：通知面极小
- 六项中仅**主动私聊**（含补句）真正发系统通知：`MainViewModel.kt:1265-1267`、`:1379-1381`（`RhodesNotificationCenter.kt:21-58`）。
- 动态定时回复（评论）、记忆维护、每日动态（广场 feed 刷新 `refreshMomentsNow` `:1211`）、手动回复（走常规私聊回复通知 `ChatViewModel.kt:2052-2059` 的既有路径）均无专属通知。
- iOS 侧通知层为聊天功能必建，A7 弃项只需移除 2 个调用点。

### 发现 3：耐用 ReplyTurn 协议在 shared 层
- `ReplyTurnRepository` / `replyTurns.claim/complete/release` 位于 `shared/src/commonMain/.../data/ChatRepository.kt:51`、`:330-333`，不依赖 Android——MomentReplyWorker 与 ManualReplyWorker 的租约/重试协议随共享层自然移植，无需重写。

## 2. 耦合分析：拆分「只保留两项」需要改动的代码面

按 5 个轴评估 6 项共享程度（H=高度共享，需整体搬动；M=中度；L=独立）。

### a) 调度注册与取消逻辑 —— 共享度 L（薄层）
- 5 个 Scheduler 是**相互独立的 object**，无共享注册模块；共用模式仅为「`enqueueUniqueWork` + Constraints + 退避」三行惯用法（`MomentReplyWorker.kt:16-21`、`ContextMaintenanceWorker.kt:16-21`、`ManualReplyScheduler.kt:20-25`、`DailyContentScheduler.kt:205-211`、`GroupAutoChatScheduler.kt:124-129`）。
- 共享点仅 2 处：启动重挂块 `MainViewModel.kt:620-639`、应用启动 `RhodesApplication.kt:81-83`。
- 拆分改动面：iOS 新建一个通用「延迟任务层」（唯一键 + 延迟 + 重试 + 前台补算队列，供 A1 群聊与 A7 两项共用）；启动重挂块只保留 628-639 三行中前两段。**不动** 计划器与手动回复调度器。

### b) 提示词管线 —— 共享度 M（两项保留项与弃项管线相互独立，但与前台功能高度共享）
- 动态回复：「moment_comment」模板（`PromptTemplates.kt:16` 分发；`MainViewModel.kt:2987` 取用）+ `buildCommenterMemoryContext` + 知识库 + 社交上下文（`MainViewModel.kt:2954-3022`）。**与动态广场前台评论回复完全同一管线**（手动触发同一 `triggerSingleAiReply`），随动态广场移植。
- 记忆维护：摘要提示词内联于 `ChatViewModel.kt:541/:573`（`generateShortTermSummary`），记忆抽取走 `ingestPrivateMemoryV2`（`ChatViewModel.kt:2239`）。**与聊天主路径共用**（`ChatViewModel.kt:2776/:2804` 正常回复后同样触发）——记忆子系统移植必然带出该管线。
- 每日动态：生成复用 `generateOneForOpSync` 的 AUTO 分支（`MainViewModel.kt:1203`），与手动发动态（`:2450/:3182`）共用「moment」模板管线；弃的只是计划器 + 投递壳。
- 主动私聊：独立管线（`PRIVATE_PROACTIVE` 模板 `PromptTemplates.kt:9` + `sendProactiveMessage` 约 30 个替换变量 `:922-950` + `buildProactiveContext :1120`），但与私聊回复基础设施（离线/在线响应模型、记忆注入 `memoryV2Pipeline.buildPrivateMemoryContext :909`）同源。
- 免打扰/手动回复：无专属提示词。
- 结论：**保留两项所需的提示词管线并不因为弃 4 项而缩小**（moment_comment、摘要/记忆管线都必须移植），弃项带来的增量是「proactive 模板 + 计划器」，不是整条管线。

### c) 记忆读写 —— 共享度 H（全在记忆子系统内，均为既有前台路径）
- 动态回复：`memoryV2Pipeline.ingestMomentComment`（`MainViewModel.kt:2932`）+ `buildCommenterMemoryContext`。
- 记忆维护：`ingestPrivateMemoryV2` + `generateShortTermSummary` + 游标/纪元设置（`ChatViewModel.kt:2222-2267`）。
- 每日动态：`ingestMoment`（`MainViewModel.kt:2639`）。
- 主动私聊：`buildPrivateMemoryContext`（`MainViewModel.kt:909`）只读召回。
- 无一项是 A7 独有写入；拆分不影响记忆子系统移植面。

### d) 通知 —— 共享度 L
- 仅主动私聊 2 个调用点（`MainViewModel.kt:1265/:1380`）为弃项专属；iOS 通知层为聊天必建。拆分 = 删 2 行接入。

### e) 设置项 —— 共享度 M（存储必建，UI 局部）
- 设置存储层（`shared/src/commonMain/.../settings/SettingsRepository.kt`）全部随共享层移植。A7 相关键：`autoAiEnabled :506`、`dailyAutoMomentEnabled :510`、`idleProactiveChatEnabled :514`、`proactiveQuietAfterUserMinutes :534`、`groupChatMinInterval :612`、`groupChatMaxInterval :616`、`groupAutoMaxRounds :620`、`dailyMomentTarget :778`、`dailyProactiveMax :792`、`proactivePerOperatorDailyMax :797`、`proactiveFollowUpChance :802`、`proactiveMinGapMinutes :812`、`quietHoursEnabled/Start/End :827-835`、`summaryAutoRetryEnabled :169`、权限函数 `getOperatorMsgPermission :1146`、`getOperatorDynPermission :1166`、`getGroupAuto :1178`。
- 拆分改动面：设置 UI 仅 `DailyContentSettingsScreen.kt`（53-119，免打扰/主动私聊/每日动态设置页）+ `SettingsScreen.kt:122` 的「每日自动内容」入口需隐藏；动态回复（`commentContextCount` 等）与记忆维护（`summaryAutoRetryEnabled`）设置本就在动态/记忆设置页，不额外动。

### 拆分所需改动代码面清单（结论）
1. iOS 通用延迟任务层（新写，A1/A7 共用）：唯一键队列 + 延迟 + 指数退避 + 「前台补算」入口（对应 `MainViewModel.kt:620-639` 重挂块 + `RhodesApplication.kt:81` 钩子）。
2. MomentReply 胶水：重挂 + `executeMomentReplyTask` 语义 + ReplyTurn 租约（共享层已有）。
3. ContextMaintenance 胶水：重挂 + `runContextMaintenance` 调用（管线随记忆子系统移植）。
4. 删除/不建：`DailyContentScheduler.kt`（256 行）、`DailyContentWorker.kt`（57）、`DailyPlanDiagnostics.kt`（65）、`ManualReplyScheduler/Worker.kt`（145）、`sendProactiveMessage`+`buildProactiveContext`+proactive 模板与 2 个通知点、`avoidQuietHours`、`DailyContentSettingsScreen.kt` 对应控件。
5. 上述清单里**没有任何一条要求先移植整个调度栈**：被弃项依赖的是「一次性延迟任务」这一最小原语，与保留项完全相同。

### 触发条件判定
- 比值：拆分/整体 = 5.0–7.5 / 11.5–17.0 ≈ **43%–65%**。
- 悲观口径（拆分取上限、整体取下限）：7.5 / 11.5 ≈ **65%**，仍 < 80%。
- 结构性原因（即使估算偏差 ±50% 也不翻转结论）：
  1. 拆分必须的「调度栈」= 一次性延迟任务原语，为 6 项共用最小集，且与 A1 共享，成本上限锁定在 ~2.5 代理日；
  2. 两项保留功能的提示词/记忆管线是动态广场、记忆子系统的前台路径，无论 A7 怎么裁都要移植（0 增量）；
  3. 4 项弃项的增量是领域逻辑（~600 行计划器/主动生成 + 1 页设置 UI），与「搬动调度栈」无关——拆分根本不涉及搬动整个调度栈。

### 建议
1. **按拆分执行**：A7 范围 = 动态定时回复 + 记忆维护（+ 启动重挂语义，属聊天核心）；预算按计划书「整体移植」口径保留缓冲不动，实际完成时提前交付。
2. iOS 后台语义层设计为**通用延迟任务层**（接口同构于 WorkManager 的 `enqueueUniqueWork`），A1 群聊自动互动先行落地，A7 复用；保留「前台补算」入口 = 每次 app 激活时扫描 pending 项（对应 Android `MainViewModel.kt:620-639`）。
3. 二期候选（每日动态/主动私聊/免打扰/手动回复）冻结不动；若产品后续要求，因调度层与管线已在，增量为 §4 表右半（6.5–9.5 代理日），无需重建基础设施。
