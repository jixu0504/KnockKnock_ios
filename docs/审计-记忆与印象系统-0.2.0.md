## 0. 结论速览

**记忆子系统「该有的零件几乎都有，但长期链路没有真正通电」。**

1. **架构完整度不错**：三层记忆（L1 碎片 → L2 中期 → L3 长期）＋ 六类来源 ＋ 本地/第三方双嵌入 ＋ 删除传播 ＋ 记忆管理 UI，规格卡（`specs/memory-v2-spec.md` 25 条契约）写得很细，金样与矩阵测试齐全。
2. **但作为「长期使用」的产品，真正决定长期体验的四条链路全部是断的或不可达**：
   - **晋升**：分组键是「内容指纹」而非主题 → L2 基本不可达，L3 实质不可达（§3.1）。
   - **滚动摘要**：`ContextMaintenanceTask` 的 5 个触发点在 iOS 端 **0 个调用点** → `SHORT_TERM_SUMMARY` 永远是「无」（§3.2）。
   - **过期/清理**：`cleanupExpiredData()` 在 iOS **从未被调用**，默认保留期又是「永久」→ 只进不出（§3.3）。
   - **索引重建**：换嵌入模型或恢复备份后，历史向量全部失效，而 `getActiveMemoryItemsMissingVector` / `memoryIndexStates` 在 iOS **0 调用点** → 静默失忆（§3.4、§3.5）。
3. **「印象系统」不是独立系统，而是 `memory_items` 的一个只读过滤视图**：没有独立数据模型、没有证据链、没有置信度、不可编辑、不体现关系演化。它的三个段落里，「长期印象／持续了解」在真实数据下长期为空，实际只有「互动印象」在无限堆积（§4）。
4. **可观测性为零**：`MemoryDiagnostics` 设计良好（窗口/耗时/token/丢弃数/operation 时间线），但 iOS 宿主**从未 `install` sink** → 全部日志被丢弃；token 用量统计也从未写入（§3.8）。任何「记忆为什么没生效」的问题，用户和开发都查不出来。

一句话：**当前版本里，「记得住」≈「最近 15 轮原文历史 + 最多 4 条相关碎片」**；跨周、跨月的人格化记忆与印象演化，基本没有发生。

## 2. 设计上被继承的历史包袱（解释「为什么会长成这样」）

1. **Android oracle 逐行移植优先于产品目标**：规格卡把「与 oracle 逐行一致」当成验收金标准（`specs/memory-v2-spec.md` 契约 1-25 全带 oracle 行号），于是 oracle 的缺陷（topicKey ≈ 内容指纹、印象页只读、单 topic 晋升）被完整继承；而 oracle 依赖的**平台侧调度与重建**（`MainViewModel.kt:731` 的 cleanup、`:1732` 的向量重建）没有一起移植。
2. **验收方式是「矩阵 + 金样」，不是「长期使用回放」**：所有召回测试用**手写 fixture 的 similarity 值**（`MemoryRecallGoldenTest`），晋升测试用**逐字相同的 20 条内容**（`MemoryParsePromotionTest.kt:156`），印象测试用**手写的 3 条夹具**（`ImpressionsBridge.kt:194-205`）。这类测试保证了「与 oracle 一致」，但**天然测不出「真实数据下长期不可达」**。
3. **端到端接线没有验收项**：`ContextMaintenanceTask`、`CleanupRepository`、`MemoryDiagnostics`、`getActiveMemoryItemsMissingVector` 都有完整实现和单元测试，但都缺「宿主调用点」；验收表里没有「这些函数在 App 里被调用」这一项。

## 3. 缺陷清单（按对「长期使用」的破坏力排序）

### P0-1｜晋升分组键是「内容指纹」，L2/L3 在自然对话中几乎不可达

- 机制：`topicKey = 类型组 + 内容前 8 个 2-gram（去噪后，≤24 字）`（`MemoryParseRules.kt:243-260`），而分组是 `groupBy { topicKey(...) }`（`:214`）。
- 实测（按同一算法在 Python 复算）：

  | 记忆内容 | 生成的 topicKey |
  |---|---|
  | 用户喜欢吃辣 | `preference:户喜喜欢欢吃吃辣` |
  | 用户很喜欢吃辣 | `preference:户很很喜喜欢欢吃吃辣` |
  | 用户今天说喜欢吃辣 | `preference:户今天说说喜喜欢欢吃吃辣` |
  | 用户其实不太能吃辣 | `preference:户其其实实不不太太能能吃吃辣` |
  | 答应周六晚上一起去看电影 | `plan:答应应周周六六晚晚上上一一起起去` |
  | 答应周六一起去看电影 | `plan:答应应周周六六一一起起去去看看电` |

  六条语义几乎相同的记忆 → **六个不同的组**。组门要求「同组 ≥20 条（普通）」或「≥2 条且含强信号」，因此：
  - **普通类型（偏好/事件/情绪/评价）的 L2：需要 20 条措辞几乎逐字相同的 L1——实际不可达**；
  - **强信号类型（承诺/提醒/importance≥80/unmet_need）：组门降为 2，即需要 2 条同前缀——只有模型两次抽出几乎同一句话时才成立，概率很低**；
  - L3：组门 10 条同 topicKey 的 L2（强信号同样降为 2），再叠加稳定性门（必须含稳定类型，且「时间跨度≥3 天 / ≥4 条 / importance≥90」之一；不足 3 条时还要有 importance≥85）。L2 每次只能产出 ≤2 条且会消耗 12 条父项并归档，因此**普通路径需要 ≥100 条同前缀 L1；强信号路径也要求同一句强承诺被反复抽出至少 2–4 次并跨 3 天**——在自然对话里基本不会发生。
- 证据：`MemoryParseRules.kt:210-227, 243-260`；单窗口最多 5 条 L1（`:295`）；阈值默认 20/10/2（`SettingsRepository.kt:436-447`）；测试用 20 条同内容才达标（`MemoryParsePromotionTest.kt:156`）。
- 长期影响：**「持续了解 / 长期印象」长期空白**；`LONG_TERM_IMPRESSION` 注入恒为「无」（`PrivatePromptWiring.kt:119-121` + `MemoryRecallEngine.kt:249-254`）；角色永远停留在「只认识你最近说的话」。

### P0-2｜滚动摘要与记忆维护在 iOS 端从未运行

- 机制：摘要生成器 `A7RealSummaryGenerator` 存在且完整（`A7Ports.kt:165-260`），维护任务 `ContextMaintenanceTask` 存在且完整（`ContextMaintenanceTask.kt`），并且在 `A7Glue` 构造、注册到延迟任务层、启动时 reconcile（`A7Glue.kt:119-131, 156, 234`）。
- 断点：把维护任务「排进队列」的 5 个触发点——`onPrivateContextChanged` / `onGroupContextChanged` / `onForegroundReplyCompleted` / `onSummaryFailure` / `maintainNow`（`ContextMaintenanceTask.kt:243-276`）——**全仓无 iOS 调用点**（`grep` 结果为 0）；`startupReconcileRecords` 只在「已有 rebuild pending 或摘要 failed」时恢复（`:212-236`），而没有触发点就永远不会产生这两种状态。
- 证据：`A7Glue.kt:156` 只注册了 handler，`A7Glue.kt:234` 只做 reconcile；没有任何地方 enqueue；Swift 侧只调用 `catchUpNow`（`AppGraphClient.swift:1043`），catch-up 也只执行「已排队」的任务。
- 长期影响：
  - `SHORT_TERM_SUMMARY` 永远为「无」（`PrivatePromptWiring.kt:115-117` 只读不写）→ **没有中期摘要**，长对话只有 15 轮原文窗口（`SettingsRepository.kt:204-207`）＋ ≤4 条碎片；
  - `retryPendingSources` 从不执行（`ContextMaintenanceTask.kt:505-510`）→ 失败窗口的重试只能靠「用户继续说话时重新 ingest」这一条路；
  - 编辑历史消息触发的「记忆重建 / 时间线 epoch 推进」永不发生。

### P0-3｜备份恢复之后 = 记忆失忆（只移植了「清索引」没移植「重建索引」）

- 机制：恢复时先 `deleteAllVectorMemories()`（`BackupFullRestoreExecutor.kt:86`），再插入记忆行并把 **L2/L3 强制改成 `status="archived"`、所有行 `vectorId=""`**（`:315, :330`；文件头注释 `:24` 明确写了这是 oracle 行为）。
- 后果：
  - 召回只读 `vector_memories`，该表已被清空；而 iOS **没有任何重建入口**（见 P0-4）→ **恢复后所有记忆召回为空**；
  - `archived` 的 L2/L3 被印象页过滤掉（`ImpressionsBridge.kt:62-69` 要求 `status=active`）→ **长期印象/持续了解在恢复后直接消失**；
  - 记忆管理页仍能看到这些行（它不过滤 active），于是用户看到「记忆都在，但角色不记得」。
- 在 Android oracle 里这个「副作用」是被 `MainViewModel.kt:1732` 的 `getActiveMemoryItemsMissingVector` 重建兜住的；iOS 只搬了问题，没搬解药。

### P0-4｜换嵌入模型 / 切第三方模式 → 历史记忆静默失忆，且无重建入口

- 机制：向量签名 = `mode|baseUrl|modelName[|protocol]`（`EmbeddingConfigurationSignature.kt`），检索 SQL 强制 `embeddingSignature = ?`（`VectorMemories.sq:63-92`）；`MemoryVectorService.search` 在签名漂移时直接返回空（`MemoryVectorService.kt:82-92`）。
- 断点：重建所需的两个方法 `getActiveMemoryItemsMissingVector`、`memoryIndexStates` 在 shared 里齐备（`MemoryV2Repository.kt:102-104, 259-263`），但**只有 Android oracle 调用它们**（`android-oracle/.../MainViewModel.kt:1582, 1732`）；iOS 全仓 0 调用点。
- 长期影响：默认 `local` 模式（`SettingsRepository.kt:862-863`）下用户一旦按引导切到第三方真语义嵌入（这是提升召回质量的**唯一**出路，见 P1-1），**过去所有记忆立刻不可召回，且永远不恢复**；反之亦然。备份恢复同理。

### P0-5｜事实冲突／变更没有任何覆盖机制

- 机制：L1 提取只发「本窗口 12 条消息」，**不携带旧记忆**（`MemoryV2Pipeline.kt:600-615`）；L1 模板里那句「如果新内容与旧印象冲突，以新内容为准描述事实，不要并列保留矛盾」（`MemoryV2PromptTemplates.kt:64`）**没有可用的旧印象**，属于无法执行的指令。
- 入库去重是 SQL 精确匹配，且 key 里包含 `sourceRefId`／`sessionId`（`MemoryV2Repository.kt:57-64`；`MemoryItems.sq:173-178`）→ **跨窗口的同义事实永远是新行**；晋升时 importance 取「子项与父项最大值」（`MemoryParseRules.kt:273-277`）→ 旧结论不会被压低。
- 长期影响：搬家、换工作、分手、改口味之后，**旧事实与新事实长期并存**，召回时随机命中其一；`LONG_TERM_IMPRESSION` 若存在也会保留旧结论。这是长期陪伴类产品最伤「人设可信度」的问题。

### P1-1｜默认召回是「字面重合」而非语义，且候选被重要性/时间预截断

- 默认 `vector_provider_mode = local`（`SettingsRepository.kt:862-863`）→ `LocalHashEmbeddingGateway`：384 维、单字/2-gram/3-gram 的 FNV-1a 特征哈希 + 符号、L2 归一（`LocalHashEmbeddingGateway.kt:6-27`）。它**没有词表、没有 IDF、没有同义词、没有否定**：「不喜欢」和「喜欢」共享「喜欢」2-gram，否定不产生排斥；384 维对中文 n-gram 存在大量碰撞。
- 阈值是**绝对余弦** 0.14/0.18/0.20/0.22（`MemoryRecallEngine.kt:133-143`），而该算法的余弦与 query 长度强相关（等权 n-gram，cos ≈ 共享 gram 数 / √(n_q·n_m)）。query 是 3 条 ×120 字（≈1000+ gram），记忆侧还带着 `"[日期·来源] "` 前缀一起被嵌入（`MemoryVectorFormatter.kt:7-27`）→ **长 query 时阈值实际极难通过，短 query 时底噪又容易通过**。阈值从未用真实分布校准过（金样测试直接给定 similarity）。
- 候选集不是「语义预筛」而是 **SQL 按 createdAt/importance 截断**（`VectorMemories.sq:63-92`）：新库 `recentL1` 取最新 150 条，老库 `olderL1` 取 importance 最高的 50 条 → 长期使用后，**低重要度旧记忆即使语义完全匹配也永远进不了候选**（静默遗忘）。
- 长期影响：角色经常「你上周刚说过」记不住，或者翻出一件毫不相关的事；用户唯一解法是自行配置第三方嵌入，而配置后又会踩 P0-4 失忆。

**补充（v1.1）**：「字面相似 ≈ 语义相似」这一点在**否定、程度、时间变化**上尤其危险——
`用户喜欢吃辣` / `用户不喜欢吃辣` / `用户以前喜欢吃辣现在不喜欢了` 三条内容共享大量 2-gram，
在该嵌入下余弦相近，而系统当前既没有极性字段、也没有事实结构，一旦用它做「自动合并」或
「去重」就会把相反事实合并成一条。这也是计划书 v1.1 把「向量相似度不得单独授权合并（原则 P3 / §4.2 三级去重）」
写进设计原则的直接原因。

### P1-2｜没有反馈闭环：记忆「只进不出」，从不学习哪些记忆真的有用

- `lastUsedAt` / `usedCount` 字段齐备（`MemoryV2.kt:33-34`），`markMemoryItemUsed` 三层实现齐备（`MemoryItems.sq` / `MemoryV2Repository.kt:406-408` / `ChatRepository.kt:677`），**全仓 0 调用点**；召回评分公式也不含使用度（`MemoryRecallEngine.kt:149-162`）。
- 没有任何「这条记忆到底影响了回复没有」的信号，也没有「这条记忆被反复召回但没用 → 降权/淘汰」的机制。结果：噪声和精华同权，只能靠模型给的 importance（不可校准）排序。

### P1-3｜存储与内存无界增长（长期使用会拖垮体验）

| 项 | 事实 | 长期量级（估算） |
|---|---|---|
| L1 默认永不过期 | `expiresAtFor` 用 `cleanDaysMemoryItems`，默认 -1 → `Long.MAX_VALUE`（`MemoryParseRules.kt:203-206`；`SettingsRepository.kt:1020, 1048`） | 每 12 条消息 ≤5 行；100 条/天 → ≈40 行/天 → **≈1.5 万行/年/角色** |
| 清理器不运行 | `cleanupExpiredData()` 仅被 Android oracle 调用（`CleanupRepository.kt:14-21`）；iOS 0 调用点；且它只是 `status='expired'` 软删，不真删行 | 行只增不减 |
| 嵌入以 JSON 文本存行内 | `embeddingJson TEXT`（`VectorMemories.sq:9`），384 个 double 的 JSON ≈ **7.5–8 KB/行** | 1 万条 ≈ **80 MB**；3 个常聊角色 ≈ 240 MB |
| 源窗口全文存 30 天再删，但删除逻辑在清理器里 | `deleteProcessedMemorySourcesBefore(now-30d)`（`CleanupRepository.kt:20`）→ 不运行 | 每行 ≈3 KB，≈8 行/天 → 额外十几 MB/年 |
| 每次召回解码 | balanced 约 320 行 × 8 KB ≈ 2.5 MB JSON 解析 + 余弦（`LocalVectorStoreGateway.kt:189-236`） | 每轮固定开销，随库增大线性恶化 |
| 印象页无分页 | 桥返回全量，Swift 全量渲染（`ImpressionsBridge.kt:57-130`；`ImpressionsView.swift:127+`） | 一年后单角色数百条 L1 印象、跨角色数千条 |
| 记忆管理页全表内存过滤 | `getAllMemoryItems()` 后内存筛选/分页（`MemoryBridge.kt:434`；`memory-ui-spec.md` §7.4 自认） | 上万行后首屏明显卡顿 |

### P1-4｜失败与降级全静默，诊断能力为零

- 召回/向量路径全用 `runCatching { … }.getOrDefault(emptyList())`（`MemoryRecallEngine.kt:109-117`、`MemoryVectorService.kt:82-92`），把超时、签名漂移、嵌入不可用都抹成「空」；用户只看到「没有相关记忆」。
- `MemoryDiagnostics` 有完整设计（operation 时间线、耗时、token、丢弃数），但 **iOS 宿主从未 `install`/`installOperations`**（`MemoryDiagnostics.kt:26-37` 的 install 在全仓只有测试调用）→ `log()` 全是 no-op。
- `LocalVectorStoreGateway.diagnose()`（候选数/解码失败/维度不匹配/耗时）已实现，**0 调用点**。
- token 统计：`addInputTokenCount` 等写入函数**全仓 0 调用点**（`SettingsRepository.kt:1376-1392`），而 `AIService` 明明返回了 usage → 消费统计页面恒为 0，**记忆的额外成本完全不可见**。

### P1-5｜晋升证据按下标对齐，存在「挂错父项」的正确性 bug

- `parsePromotionItems` 用 `parsed.mapIndexedNotNull { index, item -> objects.getOrNull(index) … }` 把「解析后的第 i 条」与「模型原始数组的第 i 条」对齐（`MemoryParseRules.kt:138-147`）。但 `parseMemoryItems` 会丢弃非法项（`:43`）并 `distinctBy` 去重（`:93`）→ 一旦有丢弃，**下标整体错位**：evidence_ids 被挂到错误父项，或本条因 evidence 为空被丢弃。
- 影响：`memory_links` 关系错误 → 删除传播会归档错误的派生记忆；L2/L3 的 `sourceRefId/sessionId` 继承错父项（`withPromotionMeta:280-281`）→ 删会话时清理对象错位。
- 现有测试 3 条全合法，覆盖不到这个错位。

### P1-6｜印象页与记忆设置的产品面过窄

- 印象页：**只读**（`oracle 的编辑/删除/清空未移植`，`specs/ranking-impressions-spec.md` §6.6）；不能纠错、不能删除、不能看证据（DTO 无 evidence 字段）；按层级分段而不是按角色分段，同一角色散在三段、跨角色交错（`ImpressionsBridge` 扁平化 + Swift 按 level 分组）。
- 记忆设置：**没有独立设置页**。`memory_v2_enabled` / 召回模式 / 晋升阈值 / 保留期 / 按来源召回开关全都没有 UI；唯一的隐私开关（「区分私密记忆」）埋在**某一条记忆的详情页**里（`MemoryListView.swift:618-663`），而且这个键对 V2 记忆**没有作用**——全仓只有 `AnchorRepository.kt:83`（legacy 锚点）读它。
- 手动记忆：桥有 `create`（`MemoryBridge.kt:221`）但**没有入口**（`memory-ui-spec.md` §7.5 自认）；没有「清空某角色全部记忆」「导出/导入某角色记忆」。

## 4. 「印象系统」专项评估

| 维度 | 现状 | 评价 |
|---|---|---|
| 数据独立性 | 无独立模型，是 `memory_items` 的只读视图 | ✗ 无法表达「印象」特有的东西：语气、亲密度、关系叙事、矛盾状态 |
| 生产者 | L2/L3 晋升（实际不可达）＋ 旧版 `memories`（iOS 上只有手动 create 会写） | ✗ 主流程几乎无生产者 |
| 覆盖面 | 只收 `PRIVATE_CHAT` | ✗ 群聊、日记、动态产生的记忆永远不进印象 |
| 可解释性 | 无证据链、无置信度、无时间跨度（DTO 只有 level/type/importance/date） | ✗ 用户看到「干员觉得你嘴硬心软」却不知道为什么 |
| 可纠错性 | 只读，不能删/改 | ✗ 错误印象只能去记忆管理页大海捞针 |
| 演化表达 | 按 L1/L2/L3 分段堆叠，不按角色/时间线 | ✗ 看不出「从陌生到熟悉」 |
| 噪声控制 | L1 段无重要度门槛，任何 `preference_expression/emotion_state/physiological_state` 都算印象 | ✗ 一年后数千条「互动印象」 |
| 验证方式 | 手写 3 条夹具（1 L1 + 1 L2 + 1 L3）断言分组/排序 | ✗ 从未端到端验证「晋升产物 → 印象页」 |

**结论**：目前它是一个「记忆台账的第三个视图」，而不是用户心智中的「这个角色怎么看我」。要让它成为产品差异化点，必须把它升级为独立实体（见 §5-C1）。

### C. 结构性重构（把它做成「长期陪伴」的护城河）

**C1. 印象升级为一等公民（最重要）**

新增独立实体 `character_impression`：
```
id, characterId, subjectType(user|world|relationship),
statement（一句自然语言，角色视角）, tone(positive/neutral/negative/mixed),
confidence(0-1), evidenceMemoryIds[], sourceSessionIds[],
firstSeenAt, lastConfirmedAt, mentionCount, supersededById, editable
```
- 写入：由「晋升 worker」在 L2/L3 之上做一次「印象合成」（每角色每天/每 N 轮一次，而非每次提取）；
- 读取：印象页按**角色**分组 + 时间线，显示「形成于 3 月 · 最近确认 5 天前 · 来自 7 次对话」；
- 纠错：每条可「不对」→ 归档该印象 + 打标，后续合成避开同类；
- 与好感度/关系网联动：亲密度变化触发「印象重估」（陌生期只允许 `event` 级印象，熟悉后才允许人格级结论）。

**C2. 记忆分层重构为「用户画像层 / 角色私有层 / 世界层」**

现在所有记忆都挂在 `ownerType=operator`，「用户是谁」这件事被每个角色各自重学一遍（147 个角色 × 各自的偏好记忆）。
建议：
- **用户画像层**（跨角色共享、用户可编辑）：姓名/称呼/生日/时区/职业/禁忌/过敏/长期偏好 —— 一次确认，全角色可用；
- **角色私有层**：该角色与用户的共同经历、约定、关系记忆；
- **世界层**：动态/群聊/日记的公共事实（已有 `ownerType=global/public`，可直接沿用）。

**C3. 记忆设置页面（用户信任的基础）**

一个页面解决：记忆总开关 / 按来源生成与召回开关 / 召回模式（省/标准/深，暴露为「记得少/正常/记得多」）/ 保留期（L1 30/90 天/永久，L2/L3 永久）/ 「重建索引」/「记忆体检」（条数、索引状态、失败窗口数、本月模型调用次数与估算费用、最近召回明细）/「清空本角色记忆」。

**C4. 评估体系（否则所有改动都无法验收）**

- 构造 20–50 组「长期对话回放集」（同一用户 × 同一角色 × 数十轮），人工标注「第 N 轮该记得什么」；
- 指标：`recall precision@k`、`矛盾率`（新旧事实并存比例）、`印象覆盖率/准确率`（每 30 轮应形成几条、人工评分）、`冷启动到第一条长期印象的轮数`、`单轮记忆注入 token`、`召回 P95 延迟`；
- 门禁：现有「oracle 金样」保留做 parity，但**长期指标进 CI**，避免再次出现「测试全绿、产品不可用」。

## 7. 结论修订（v1.1）

外部审阅促使本报告把结论从「能力缺失」进一步收敛为**优先级排序**：

> **先保证记忆正确、可解释、可恢复、不越权；再追求记忆数量、复杂度与智能程度。**

具体到本项目：

1. **P0 级里最重要的是「正确性」而非「召回率」**：晋升分组失效（M-01）、事实变更无覆盖（M-05）、恢复/换模型失忆（M-03/M-04）会直接让角色「记错」或「失忆」，而召回率低只是「记不住」——前者伤害信任，后者可以靠重复对话补救。
2. **隐私边界需要独立于召回质量治理**：`privacy` 字段的语义混用（X-02）必须在数据模型层解决，不能只靠开关。
3. **可观测性是一切改进的前提**：M-09 不修，任何 Gate 指标都不可信。
4. **审计本身也要能被验证**：本报告的静态推算已标注，计划书 v1.1 的 Gate 全部改为实测项，禁止用审计中的推算数字当基线。

## 附录 B：本报告中的估算口径

- 「≈1.5 万行/年/角色」：假设 100 条消息/天、每 12 条消息一个窗口、每窗口平均 4 条有效 L1、每年 365 天 → 100/12×4×365 ≈ 1.2 万（取整为万级）。
- 「≈80 MB/万条」：384 维 double 的 JSON 文本 ≈ 19 字符/值（含分隔符）×384 ≈ 7.3 KB，加行开销取 8 KB。
- 「每次召回 ≈2.5 MB 解码」：balanced 模式 5 桶上限 150+50+60+30+30=320 行 × 8 KB。
- 「L2/L3 不可达」：基于 topicKey 精确相等分组的确定性推断，非概率证明；即使极端重复场景可达，也属「重复驱动」而非「主题驱动」，产品语义仍不成立。
